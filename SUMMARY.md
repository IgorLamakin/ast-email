# АСТ Email Templates — сводка проделанной работы

Документ описывает путь проекта от исходного архива (`v32`) до текущего состояния
(версия `2.2.1` установлена, версия `2.3.0` в разработке). Подробности по каждой
версии — в `CHANGELOG.md`, здесь — обзор для понимания общей картины.

---

## 1. Что это за проект

Десктоп-приложение на Windows (Electron) для рассылки типовых email-писем
сотрудниками компании АСТ (промышленная автоматизация, КИПиА/АСУТП):
- Бэкенд — Python/FastAPI + SQLite, работает локально на компьютере пользователя.
- Фронтенд — React (Vite), встроен в Electron-окно.
- Функции: регистрация/роли (админ/сотрудник), блочный конструктор писем,
  адресная книга контактов, отправка через SMTP, аналитика отправок.

## 2. Изначальный аудит (архив v32 → v32-fixed, версия 2.0.0)

Полный список — в `audit-i-plan-ispravleniy.md` и `CHANGELOG-ispravleniy.md`.
Кратко, самое критичное:

- **Рассинхронизация фронтенда и бэкенда**: фронтенд обращался к
  несуществующим маршрутам (`/templates/common`, `/email/preview`,
  `PUT /auth/me` и др.) — часть функций (сохранение профиля, публикация
  шаблонов, предпросмотр) не работала вообще.
- **Ложный "успех" при неотправленном письме**: если SMTP не был настроен,
  бэкенд всё равно отвечал "письмо отправлено".
- **Дыры в безопасности**: захардкоженный `SECRET_KEY` в исходниках (можно
  подделать токен администратора), любой зарегистрировавшийся получал права
  admin, срок жизни токена не совпадал с заявленным.
- **Дублирование стандартных шаблонов** при каждом перезапуске бэкенда.
- **Удаление шаблона ломало всю страницу аналитики** (не было "снимка"
  названия шаблона на момент отправки).
- **Смешение абсолютных/относительных путей** к API — часть функций работала
  в дев-режиме, но ломалась в собранном `.exe`.
- Более 60 автоматических тестов на реальном коде подтвердили исправления
  (подробности в переписке и `CHANGELOG-ispravleniy.md`).

## 3. Сборка в десктоп-приложение и живая отладка (2.0.0 → 2.1.0)

Процесс превращения кода в установщик `.exe` выявил ещё несколько живых багов,
которые не были видны при статическом анализе:

- Приложение не устанавливало Python-зависимости бэкенда само — добавлена
  автоустановка при первом запуске (с экраном загрузки).
- `.bat`-скрипты не запускались (`"я╗┐@echo" is not recognized`) — оказалось,
  в начале файлов был невидимый BOM-символ, ломавший разбор командной строки.
  Исправлено во всех `.bat`.
- После нажатия "Готово" в мастере настройки приложение иногда не открывалось
  само — причина: окно мастера закрывалось раньше, чем появлялось основное
  окно, и Electron воспринимал это как "все окна закрыты" и завершал процесс.
- Стандартные шаблоны не появлялись после регистрации первого пользователя на
  свежей базе (порядок вызовов при самом первом запуске).
- Diagnostика реальной сети/SMTP (Yandex DNS-аномалия, смена на Mail.ru).

## 4. Редизайн и новые разделы (2.1.0)

- **Новый визуальный стиль**: боковое меню вместо верхнего, цветовая палитра
  под тематику компании (графит + сигнальный оранжевый), шрифты IBM Plex
  Sans/Mono вместо дефолтных.
- **Раздел «Настройки»** — SMTP теперь можно посмотреть/поменять прямо в
  приложении (раньше — только один раз в мастере при установке). Пароль
  больше не передаётся и не хранится в открытом виде на фронтенде.
- **Раздел «Аккаунты»** (только для администратора) — все пользователи,
  сколько писем каждый отправил, какие у него шаблоны, возможность сделать
  чужой шаблон общедоступным или снять с публикации.
- Номер версии виден в самом приложении.

## 5. Система версионирования и обновлений (2.1.0)

Раньше каждое обновление требовало полного сноса и переустановки. Теперь:

- **Git** — локальная история кода, каждая версия — отдельный commit + tag
  (`v2.1.0`, `v2.2.0` и т.д.). Можно посмотреть историю (`git log --oneline`)
  и откатить код к любой версии (`git checkout vX.Y.Z`).
- **`releases/`** — папка с установщиком `.exe` каждой когда-либо выпущенной
  версии — архив версий приложения.
- **`release.bat`** — один скрипт, который сохраняет снимок в Git, собирает
  установщик и кладёт его в `releases/`. Версию и текст в `CHANGELOG.md`
  проставляет разработчик заранее — пользователю ничего вводить не нужно.
- **Обновление = запустить новый `.exe` поверх старого**, без сноса — данные
  (аккаунт, база, настройки) хранятся отдельно и не затрагиваются.
- Подробная инструкция — `VERSIONING.md`.

## 6. Этап 1 редизайна конструктора писем (2.2.0)

- Исправлены баги: белый экран при редактировании стандартных шаблонов,
  кнопка в редакторе уводила в браузер, предпросмотр не обновлялся при вводе
  email/обращения.
- **Вставка блока в любое место** — не только в конец списка.
- **Новый блок «Колонки»** — до 3 блоков в ряд, вёрстка на HTML-таблицах
  (не CSS flex/grid — иначе ломается в Outlook).
- **Настройки письма**: фон (цвет/картинка) для всего письма.
- **PDF-вложение**: переключатель у шаблона "прикладывать PDF-версию письма
  при отправке" (без кнопок — статичный PDF). Кнопка "Save to PDF" внутри
  самого письма технически невозможна — почтовые клиенты не выполняют
  JavaScript, поэтому сделано как настройка шаблона, а не как блок.
- Больше настроек блока: размер шрифта, отступ до следующего блока.

## 7. Исправление картинок (2.2.1)

Двухслойный баг, обнаруженный только при реальном использовании:
- Бэкенд отдавал относительный путь к загруженной картинке — не грузилось в
  собранном приложении. Исправлено.
- Даже с полным адресом картинка ссылалась бы на `localhost` **компьютера
  отправителя** — получатель письма не смог бы её увидеть вообще. Теперь при
  реальной отправке письма картинки (обычные и фоновые) встраиваются прямо в
  HTML письма как `data:`-URI. Уже сохранённые шаблоны с битой ссылкой чинятся
  автоматически при открытии в редакторе.

## 9. Как проверялось качество

Поскольку у меня нет доступа к Windows/Electron-рантайму напрямую, каждое
изменение бэкенда и логики фронтенда проверялось **реальным выполнением кода**
в изолированной среде (минимальные заглушки только для недоступных без
интернета библиотек типа FastAPI/SQLAlchemy — сама бизнес-логика выполнялась
без изменений). На момент версии 2.2.1 — свыше 90 автоматических проверок,
включая:
- сверку всех маршрутов фронтенд↔бэкенд,
- реальную регистрацию/роли/права доступа,
- реальную отправку письма (мокался только сетевой вызов SMTP),
- побайтовое сравнение картинки до/после встраивания в base64,
- рекурсивную работу с блоками внутри колонок.

Визуальные/интерактивные вещи (перетаскивание мышкой, точный внешний вид)
проверяются только вручную вами после сборки — здесь это принципиальное
ограничение среды, а не недосмотр.

│       ├── App.jsx             маршрутизация, разграничение admin/обычный

│   ├── main.js                 запуск бэкенда, окна, автоустановка зависимостей

**Технологии**: Python 3.12 / FastAPI / SQLAlchemy / SQLite / Jinja2 / xhtml2pdf
(бэкенд); React 18 / Vite / Tailwind / react-router (фронтенд); Electron 31 /
electron-builder + NSIS (упаковка в `.exe` для Windows); Git (версионирование
кода, локально, без внешнего сервера).

## 12. Ключевые технические решения и почему

| Решение | Почему именно так |
|---|---|
| Колонки в письме — HTML-таблицы, а не CSS flex/grid | Outlook и часть других почтовых клиентов не поддерживают современную CSS-раскладку в письмах — таблицы работают предсказуемо почти везде. |
| PDF — вложение при отправке, а не кнопка в письме | Почтовые клиенты не выполняют JavaScript — кнопка «Save to PDF» внутри письма технически не может сработать ни в одном клиенте. |
| Картинки — встраиваются как `base64` при отправке | Ссылка на `localhost` существует только на компьютере отправителя — получатель не может её открыть. Без встраивания все картинки были бы битыми у получателей. |
| PDF-библиотека — xhtml2pdf, а не weasyprint/pdfkit | Чистый Python (через reportlab), ставится через обычный `pip install` без отдельных системных библиотек/бинарников на компьютере пользователя. |
| Версионирование — Git + папка `releases/`, без электрон-автообновления | Не требует внешней инфраструктуры (сервера обновлений, GitHub-аккаунта и т.п.) — работает полностью локально на одном компьютере. |
| Вложенность блоков — только один уровень (в колонках) | Полная произвольная вложенность блоков плохо совместима с версткой email-писем и резко увеличивает сложность/риск багов; один уровень уже закрывает основной сценарий («блоки рядом»). |
| SMTP-настройки — общие на всё приложение, не персональные | Так было в исходном проекте; при необходимости расширяется до персональных настроек отдельной задачей. |

## 13. Известные ограничения (сознательно, не баги)

- **Нет доступа к реальной Windows/Electron-среде на моей стороне** — весь
  визуальный/интерактивный результат (как выглядит, как ощущается
  перетаскивание мышкой) проверяется только вами после сборки. Я проверяю
  код через реальное выполнение логики везде, где это возможно без браузера.
- **Откат установленного приложения на более старую версию** (через папку
  `releases/`) не протестирован лично мной на реальной Windows — по
  документации electron-builder/NSIS должен работать «из коробки», но стоит
  один раз проверить на низко-рискованном примере.
- **Прозрачность и градиенты в письмах** поддерживаются не всеми почтовыми
  клиентами одинаково (в первую очередь — Outlook классический); там, где
  это критично, добавляется запасной вариант (сплошной цвет вместо градиента).
- **Единый SMTP на всё приложение** — все пользователи отправляют через один
  и тот же почтовый сервер, настроенный администратором.

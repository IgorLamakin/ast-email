# План исправления ошибок — АСТ Email Templates (email-templates-project-v32-fixed)

## Контекст

Проект — десктоп-приложение (Electron + React/Vite фронтенд + FastAPI/SQLite
бэкенд) для рассылки email-писем сотрудниками ООО «АСТ». Ранее (v2.0.0–v2.2.1)
проведён большой аудит и исправлен ряд критических багов (рассинхронизация
маршрутов, хардкод `SECRET_KEY`, ложный «успех» отправки и др. — см.
`CHANGELOG-ispravleniy.md`). Сейчас в разработке версия **2.3.0**.

Этот документ — результат нового исследования кода (сентябрь 2026, три
параллельных поисковых агента по фронтенду/`BlockEditor.jsx`, бэкенду/
`main.py`+`models.py`, и Electron/сборочным скриптам), ключевые находки
проверены вручную (grep/Read). Все пункты ниже подтверждены, не являются
догадками.

Самая важная находка: **`SUMMARY.md` описывает функциональность, которой нет
в коде.** Это меняет приоритет работы — сначала нужно понять, куда делся
заявленный код, и только потом чинить остальное.

## P0 — Критично, разобрать в первую очередь

### 1. Расхождение `SUMMARY.md` и реального кода в `BlockEditor.jsx`

`SUMMARY.md` (раздел 8, версия → 2.3.0) утверждает, что три функции
реализованы («код написан, протестирована логика») либо полностью готовы:
- ✅ прозрачность блока (слайдер 10–100%),
- 🔄 resize картинки мышкой за угол со snap-сеткой (25/50/75/100%),
- 🔄 перетаскивание границы между колонками (пропорции, напр. 30/70).

Фактическая проверка `frontend/src/components/BlockEditor.jsx` (986 строк,
единственная версия файла в проекте) показала: **ни одна из трёх функций не
реализована вообще**, ни в каком виде:
- поля `opacity` нет ни в `defaultBlock` (`BlockEditor.jsx:47-54`), ни в
  панели стилей блока, ни в HTML-рендере (`renderBlocksBody`);
- ширина картинки — обычный `<select>` с 3 вариантами (`100%/75%/50%`,
  `BlockEditor.jsx:605-611`), никакой mousedown/mousemove-логики нет;
- колонки рендерятся только с равными долями: превью — `flex: 1`
  (`BlockEditor.jsx:367`), HTML для письма —
  `colWidthPct = Math.floor(100 / colCount)` (`BlockEditor.jsx:951`); у
  модели колонки (`{ blocks: [] }`, `BlockEditor.jsx:74`) вообще нет поля
  под пропорцию/ширину.

Поиск по всему `frontend/src` (`resize|mousedown|mousemove|snap|opacity`)
подтверждает — кода нет нигде в проекте, отдельных файлов-хуков/утилит для
этого тоже нет.

**Действия:**
1. Проверить git-историю на потерянную работу, прежде чем писать код заново:
   `git log --oneline -30`, `git branch -a`, `git stash list`,
   `git log --all --oneline -- frontend/src/components/BlockEditor.jsx`.
   (На момент составления плана `git`-команды были временно недоступны
   из-за сбоя окружения — эту проверку нужно выполнить в первую очередь.)
2. Если находится потерянный коммит/стэш/ветка — восстановить оттуда.
3. Если ничего не находится — считать эти три функции **не реализованными**
   (а не «сломанными») и реализовать с нуля как отдельную подзадачу:
   - `opacity` — простое поле в `styles` блока + `<input type="range">` в
     панели стилей (аналогично уже существующим `backgroundColor`/`padding`
     в `BlockEditor.jsx:727-782`) + проставление в инлайн-стиль при рендере.
   - Resize картинки — `onMouseDown` на угловом «хэндле» поверх превью
     картинки, вычисление процента по смещению курсора относительно
     контейнера, привязка к шагу 25% при `mousemove`, снятие слушателей на
     `mouseup` (через `document.addEventListener`/`removeEventListener` в
     `useEffect`, чтобы не было утечек).
   - Граница между колонками — добавить поле ширины (в % или доле) в модель
     колонки, перетаскиваемый разделитель между `<div>` колонок в превью
     (аналогично resize картинки), использовать сохранённые проценты вместо
     `Math.floor(100 / colCount)` в `renderBlocksBody`.
4. После реализации — обновить `SUMMARY.md`/`CHANGELOG.md`, чтобы описание
   снова соответствовало факту (это ценность документа — не давать ложную
   картину прогресса).

### 2. Миграция SQLite не покрывает колонку `templates.blocks`

`backend/models.py:60` — `Template.blocks = Column(Text, nullable=True)`.
`backend/main.py:100-118`, функция `_migrate_sqlite_schema()`, добавляет
через `ALTER TABLE` только `template_title`, `status` (для `email_logs`) и
`attach_pdf` (для `templates`) — **колонки `blocks` в списке нет**.
SQLAlchemy `create_all()` не изменяет уже существующие таблицы, только
создаёт отсутствующие с нуля. Любой пользователь с базой, созданной до
появления поля `blocks`, при первом же запросе к шаблонам получит
`OperationalError: no such column: templates.blocks`.

**Действие:** добавить в `_migrate_sqlite_schema()` (`backend/main.py`) ещё
один блок по аналогии с существующими:
```python
conn.exec_driver_sql("ALTER TABLE templates ADD COLUMN blocks TEXT")
```
(обёрнуть в тот же try/except-по-колонке паттерн, что уже используется для
`attach_pdf` и `template_title`).

### 3. Пароль SMTP может утечь в git через `smtp-config.bat`

`smtp-config.bat` (корень проекта) — файл с плейсхолдерами
(`SMTP_PASSWORD=ВАШ_ПАРОЛЬ_ПРИЛОЖЕНИЯ` и т.п.), который пользователь
заполняет реальными данными **прямо в этом файле** для dev-режима
(`start.bat:9-12` подгружает его через `call`, чтобы прокинуть переменные
окружения). Файл **не входит в `.gitignore`**, а `release.bat` на каждый
релиз делает `git add -A` + `git commit`. Если разработчик впишет туда
реальный пароль приложения и хоть раз запустит `release.bat` — пароль
попадёт в историю git.

**Действия:**
1. Добавить `smtp-config.bat` в `.gitignore`.
2. Создать `smtp-config.example.bat` с плейсхолдерами (без реальных данных)
   для распространения через git, а рабочий `smtp-config.bat` — только
   локально.
3. Проверить, не попал ли уже реальный пароль в существующую git-историю
   (`git log -p -- smtp-config.bat`) — если да, потребуется отдельная очистка
   истории и смена пароля приложения.

### 4. `release.bat` коммитит временный служебный файл

`scripts/get-release-info.js`, вызываемый из `release.bat:33`, создаёт
`scripts/.commit-message.tmp`. `git add -A` (`release.bat:40`) индексирует
его **до** удаления (`del`, `release.bat:50`, уже после `git commit`).
Файл не в `.gitignore`. В результате при каждом релизе служебный файл с
текстом коммита физически попадает в дерево репозитория.

**Действие:** добавить `scripts/*.tmp` в `.gitignore` (единой строкой
закроет и `.commit-message.tmp`, и уже корректно обрабатываемый
`.version.tmp`).

## P1 — Важно, но не блокирует базовую работу

### 5. `electron/main.js` — риск повтора бага «все окна закрыты» в error-ветках

В обеих error-ветках `whenReady()` (`main.js:382-392` и `398-408`, когда
`waitForBackend` возвращает `false`) порядок такой: `closeSplash()` →
`dialog.showErrorBox(...)` (синхронный, блокирует до закрытия пользователем)
→ только потом `createWizardWindow()`/`createMainWindow()`. Пока диалог
висит, открытых `BrowserWindow` временно 0 — тот же паттерн, что уже вызывал
исправленный баг с преждевременным `app.quit()` по `window-all-closed`,
просто перенесённый в другое место.

**Действие:** поменять порядок — сначала создавать
`createWizardWindow()`/`createMainWindow()`, затем показывать
`dialog.showErrorBox`.

### 6. `get_current_user()` — необработанный `ValueError` при невалидном `sub`

`backend/main.py:252`: `int(user_id)` вызывается **вне** `try/except
JWTError` (блок try заканчивается на строке 251). Если `sub` в токене не
числовой — упадёт необработанный `ValueError` → «сырая» 500 вместо
ожидаемого 401. Риск невысокий (токен подписывается самим бэкендом), но
это дефект защитного программирования на границе доверия (пользовательский
токен).

**Действие:** перенести `int(user_id)` внутрь `try` или обернуть отдельным
`try/except (ValueError, TypeError): raise credentials_exception`.

### 7. Встраивание картинок в письмо — отсутствие обработки ошибок чтения файла

`backend/main.py`, `_file_to_data_uri()` (492-503) читает файл без
try/except; вызывается из `_inline_local_images()` (506+), которая
используется в `send_email()` **до** финальной обработки ошибок отправки.
Если файл картинки повреждён/заблокирован/недоступен по правам — вылетит
необработанное исключение → 500 вместо понятного сообщения (ложного
«успеха» при этом не будет, но UX хуже, чем мог бы быть).

**Действие:** обернуть чтение файла в `_file_to_data_uri()` в try/except,
при ошибке — логировать и возвращать `None` (как уже сделано для случая
«файла нет на диске»).

### 8. Regex для встраивания фоновых картинок хрупкий

`_inline_local_images()` (`main.py:526`) ищет строго
`background-image:url('...')` с одинарными кавычками, `<img src="...">` —
строго с двойными. Сейчас `BlockEditor.jsx` (строки 920, 966) всегда
генерирует именно такой формат, поэтому на практике работает, но при любом
ручном редактировании HTML или изменении формата генератора встраивание
молча не сработает — получатель увидит битую ссылку на `localhost` без
ошибки и без лога.

**Действие:** сделать regex нечувствительным к типу кавычек (одинарные/
двойные/без кавычек), например через `['"]?` в паттерне.

### 9. Нет лимита на размер письма при base64-встраивании картинок

Каждый файл целиком читается в память и кодируется в base64 (+~33% к
размеру) без проверки суммарного размера/количества картинок. При
нескольких крупных изображениях итоговое MIME-письмо может превысить лимиты
SMTP-сервера получателя без предупреждения пользователю заранее.

**Действие:** добавить проверку суммарного размера встраиваемых картинок
перед отправкой (например, порог ~10–15 МБ) с понятной ошибкой
пользователю, если превышен.

## P2 — Мелкие/косметические

### 10. CORS: `allow_origins=["*"]` вместе с `allow_credentials=True`

`backend/main.py:202-206`. Формально некорректная комбинация по спецификации
CORS (браузеры её тоже трактуют по-разному). Для чисто Electron-окружения
(запросы идут не из произвольного веб-origin) риск низкий, но стоит сузить
`allow_origins` до реально используемых origin'ов (`http://localhost:3000`
для dev, `file://`/кастомный origin для собранного приложения).

### 11. `electron/icon.png` — заглушка

857 байт, залитый одноцветный квадрат без логотипа. Используется и как
иконка окон, и как иконка `.exe`-сборки (`electron/package.json:45`).
Не баг в смысле работоспособности, но пользователь увидит пустой квадрат
вместо логотипа компании.

**Действие:** заменить на реальную иконку (если есть брендбук АСТ) перед
следующим публичным релизом.

### 12. `electron/main.js` — `app.on('activate', ...)` рассинхронизирован с `whenReady`

Строки 420-435: дублирует логику создания окна, но без `waitForBackend` и с
«угадывающим» `setTimeout(…, 5000)` вместо ожидания реальной готовности
бэкенда. Практический риск близок к нулю, т.к. сборка идёт только под
Windows (`win: { target: "nsis" }`), а `activate` — по сути macOS-событие
(клик по иконке в доке), которое на Windows штатно не возникает.

**Действие:** низкий приоритет — либо унифицировать с основной веткой
(`whenReady`), либо убрать полностью, раз событие нерелевантно для целевой
платформы.

**Проверка после исправлений:**
- Бэкенд: `python -m py_compile backend/*.py` — синтаксис; вручную дернуть
  `/templates` на свежесозданной (без поля `blocks`) и на существующей БД

- Фронтенд: `cd frontend && npm run build` — сборка без ошибок; вручную в
